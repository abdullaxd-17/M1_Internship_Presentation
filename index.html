01 · Motivation

Why this project matters

CubeSats need their power and data subsystems validated together — on a bench, before flight.

Autonomous solar power

A flight-like node must run on harvested energy and a battery — not a lab bench supply that hides the real charger behaviour.

Integrated, not isolated

Power, sensing, firmware and radio are usually built separately. Faults appear only when they finally meet. This platform forces them to meet early.

Wireless telemetry

LoRa carries measurements over long range at low power — the right fit for a remote, energy-constrained sensing node.

Traceable & debuggable

Every stage exposes a signal you can probe — solar voltage, regulated rails, UART frames, the LoRa payload — so a fault always has somewhere to show itself.

“ The goal is a faithful, bench-sized copy of the flight energy-and-data chain — complete enough to expose every integration risk before hardware is committed to a mission.
02 · System overview

One continuous chain, two simultaneous flows

Energy path — solar to regulated rails Data path — sensors to UART telemetry Wireless path — LoRa over 868 MHz Feedback — GUI display & logging

The two flows are coupled: a LoRa transmit burst is a data event, but it also lands on the EPS as a momentary load — which is why the power budget and the comms test plan are treated together, never as separate topics.

03 · High-level architecture

Six layers · the power path and the data path, side by side

ENERGY PATH
  • Energy sourceSolar board — AZUR SPACE 3G30A cells + sun sensors
  • Power managementEPS — BQ25798 power path, battery charge, rail generation
  • Regulated rails3.3 V (logic) & 5 V (heaters/load) to the THC board
DATA PATH
  • Measurement & controlTHC — RTD temperature, INA3221 current, heater logic
  • Embedded controllerSTM32L432KC — acquire, convert, format UART frames
  • Wireless link & backendHeltec SX1276 → 868 MHz LoRa → receiver → GUI / ChirpStack
Why layers? Fault isolation. If a temperature value never reaches the GUI, I check the chain in order — EPS rails → THC supply pins → STM32 UART → Heltec serial log → RF link → GUI parser — so debugging never becomes guesswork across power, firmware and RF at the same time.

08 · EPS board — Layer 2

Electrical Power System — one BQ25798 manages everything

The charger sits between four sources and loads: solar in, USB-C in, battery, and the system bus that powers the rest of the platform.

VIN1 ← Solar VIN2 ← USB-C BAT — 1S Li-ion SYS bus 3.3 V rail 5 V rail
BQ25798 dual-input buck-boost charger · MPPT · USB-PD power path
INA260 solar-bus power & current monitor (I²C)
LTC4352 ideal-diode / power-path lane protection
BQ27441 battery fuel gauge (state-of-charge)
AP50N04QD ×2 input MOSFETs for VIN1 / VIN2 lanes
Golden rules. Solar only on VIN1, USB-C only on VIN2 — never both on one input. A regulated rail is never wired to the battery port; charging stays under BQ25798 control. The THC board is connected only after rails are verified.

Avionics use a small fraction of generation, so the chain runs with wide margin. Heater duty must be budgeted against generation and battery; the LoRa transmit spike is absorbed by the battery, not the rail.

16 · STM32 / SCM interface — Layer 4

From RTD resistance to a readable telemetry frame

1 Init clocks & peripherals (SPI / I²C / UART)
2 Configure RTD interface
3 Acquire temperature channel(s)
4 Convert resistance → °C (Callendar–Van Dusen)
5 Format ASCII payload
6 Transmit on UART, repeat every 2 s
RTD model RT = R0 (1 + A·T + B·T²) PT100 resistance solved for temperature, then validated against a known resistor before live heating.
Worked point R = 109.63 Ω → (109.63 − 100) / 0.385 → 25.0 °C → T1:25.00

21 · Testing & validation

The four-point rule — one frame, checked everywhere

A telemetry frame is only valid when the identical payload appears at all four observation points.

1STM32 UART T1:25.75,T2:0.00 Sensor + firmware OK
=
2Heltec TX log T1:25.75,T2:0.00 UART hand-off OK
=
3LoRa RX log T1:25.75,T2:0.00 RF link OK
=
4GUI display T1:25.75,T2:0.00 Parser OK
✓ Any mismatch localises the fault instantly — formatting, transmission, decoding or parsing
✓ Acceptance: stable rails · clean STM32 boot · ≥ 1 valid temperature frame · matching RX payload · RSSI/SNR logged
22 · Challenges & solutions

Design decisions and debugging

BEFORE Distributed SPV1040 charger blocks Multiple per-panel chargers — more parts, more failure points, harder routing
⟶
AFTER One BQ25798 Single device for solar + USB-C + battery + system bus, with built-in MPPT

VIN1 / VIN2 confusion

Risk of cross-wiring solar and USB-C. Fix: labelled harnesses + continuity checks before power.

Silent UART link

No frame at the Heltec. Fix: common ground, crossed TX/RX, confirmed 115200 baud.

No LoRa packet

Mismatched radio settings. Fix: match frequency, bandwidth, SF, coding rate & sync word on both ends.

None of these were design flaws — they were integration details, each one isolated to a single stage and closed before moving to the next.
